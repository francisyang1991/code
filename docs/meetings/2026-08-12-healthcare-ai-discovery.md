## 一、背景

诊所（"诊所 / 中心"）目前为小型规模，仅有数名 provider，患者数据已集中录入到一套 **OpenEMR**（开源电子病历系统）中。此前由一位在北京、拥有自有 IT 团队的朋友协助做过二次开发（新增了高级搜索功能）；该朋友现已加入一家较大的公司、精力有限，诊所因此在寻找新的 IT 力量来承接后续需求。

诊所方（高耀技师）自评："接触 IT 较多，但并非专精"，倾向于聚焦当前资源与可落地的范围；王医生则更倾向从 big picture / 长期蓝图出发。本次沟通旨在梳理需求、评估双方合作可能。

## 二、需求讨论

### 需求 1：AI 语音服务（接电话 / 打电话）—— 有需求但不紧急

**场景设想：**
- **接电话（inbound）**：AI 语音接听患者来电，通过语音交流对患者进行 **triage / 分流分类**，再转入进一步处理。
- **打电话（outbound）**：AI 主动对患者做 **follow-up / 随访**，并将随访过程中患者提到的内容、数据、主诉等自动记录下来。
- **合规约束**：涉及大量医疗信息，需重点考虑隐私保护与 **HIPAA** 合规。

**动机（为何考虑自研）：**
- 起因是王医生权衡"前台是雇人还是用 AI"，高耀技师此前做过初步调研、约过几个 demo，但未系统询价、未深挖市场玩家。
- 已接触的 vendor 体验不佳：有的已停止服务（例：某多伦多大学学生团队做的产品，疑似已停运）；有的明显 focus 在 volume 较大的大客户，小型诊所（起步阶段 volume 小）不在其目标客户范围内。
- 推测：通用大语言模型高速发展后，垂直"AI 客服/语音"公司的产品越来越难卖（抛开隐私合规，会用 LLM 的人自行搭一套应答/随访系统门槛已不高），因此部分小玩家退出；剩余玩家多服务大型 healthcare system。

**自研 vs 采购（核心待评估问题）：**
- 现成产品多为 SaaS 订阅模式，按使用 volume 付费；因同一产品可卖给多家诊所而摊薄成本。
- 诊所若"从头自研、仅供自用"，需评估人力投入、开发周期与最终成本是否划算。
- **待技术方评估**：若双方共同开发这样一套"接电话 + 打电话"系统，大概需要多少时间、多少人力、总成本大致多少。

**技术方反馈：**
- 工业界纯 AI 服务台 / AI call center 类产品（含分流、接听、随访）已相对成熟。
- 计费/交付模式分两类：大客户会派专人协助 onboarding（适合复杂系统）；SMB / 小客户可采用自助部署（vendor 提供 API 或小型软件工具，客户自行部署），成本较低；费用一般按数据量或产品复杂度计。
- 推荐诊所方了解 vendor **Crysta**（高耀技师此前看过但不熟，请技术方发送资料/名称以便进一步了解报价）。

### 需求 2：EMR 系统集成（最紧急）—— 不涉及 AI

在 OpenEMR 基础上做对外系统对接（API integration），是当前**最紧急**的需求：

- **电子处方系统集成**：EMR 与全国范围药房的电子处方系统（e-prescription）对接。
- **Billing / 理赔集成**：将就诊与检查打包成 claim（编码），通过保险的 portal / switch / clearinghouse 发送给政府保险（Medicare / Medicaid）或商业保险（UnitedHealth、Cigna、Aetna 等），并接收保险方反馈回传到 EMR，从而获知报销金额、应收款项。

**难点：**
- 电子处方等系统有一些较特殊、不完全标准化的协议：EMR 发出的 order / prescription，对方返回的结果有时不够规范，EMR 难以判断反馈是"正确 / 错误 / 仅是使用不规范"。
- 该 communication 通常需要有 integration 经验的 IT 来调试；对没做过的人存在 learning curve，会拉长集成周期，但并非无法实现。

**对 EMR 的说明（供技术方理解）：**
- EMR = Electronic Medical Record，保存患者身高、体重、就诊原因、诊断、检验检测（lab result）等全部历史医疗数据。
- 检验检测多为第三方外包（如 Quest 等）：EMR 发出 lab order → 第三方完成 → 结果回传并存入 EMR。
- Billing 只是 EMR 众多功能之一。EMR 本身不做药品推荐，主要与 billing 等系统做数据对接。
- 该需求为纯粹的 **API 集成，不涉及 AI**。

### 需求 3：基于 AI 的患者队列筛选（中长期）—— 用于临床研究

**目标：** 从 EMR 数据库中筛选出符合某项临床研究入组标准的患者。

**现状与两种方式：**
1. **Rule-based（现有）**：数据从旧诊所系统导出、迁移入 OpenEMR 时已**结构化**；很多字段（如血糖、血红蛋白等指标数值、年龄、诊断等）本身即带"标签"。朋友已开发的高级搜索功能即基于这些 tag，可对具体数值 / 年龄 / 是否患某病等**明确条件**做数据库 query，把复杂 criteria 拆成一条条条件后组合检索。
2. **AI-based（设想）**：无需逐个打标签，让 AI 直接"吃下"大量原始、未打标签的医疗记录并理解，再判断哪些患者符合研究标准。

**AI 的价值定位（双方共识）：**
- 处理 rule-based 难以覆盖的部分——大量以 **description / 自由文本**形式存在、未结构化的信息。
- 技术方提出可行方向：将数据做成**本地私有 RAG**、建 index 查询；部署**本地私有化模型**避免数据外泄；用 AI 对 transcription / 对话数据做查询并自动打标签；做 **semantic search / 模糊搜索**，找到"符合 criteria 但 rule-based 不易命中"的患者，覆盖更全面。
- 合规同样是关键约束（私有化部署以保护患者数据）。

- 技术方认同该方向，愿意 collaborate，共同把 picture 做大；同时理解高耀技师"先聚焦当前资源与可落地范围"的务实思路。
- 双方共识：先从当前实际的痛点与简单 feature 入手，逐步推进到更大蓝图。
